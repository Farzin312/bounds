# Cross-language OSS benchmark — token economics, correctness, and full-command coverage

A 16-repository sweep run to answer one question honestly: **does Bounds work on code it was not
tuned for, or is it optimized for its own repo?** It measures the token economics on real
third-party projects, exercises the *entire* command surface on each, and records every bug,
crash, or misleading output it finds. The economics are real and the extraction is correct; the
auto-`discover` → `validate`/`calibrate` drift layer is **not yet trustworthy on nested-package
layouts** — that gap is documented here in full, not hidden.

- **Date:** 2026-06-01
- **Bounds version:** `2026.6.24` (branch `agent-plugins-aliases-benchmark`)
- **Tokenizer:** `tiktoken cl100k_base` (exact) — *not* the `~4 chars/token` estimate used in the
  earlier two-repo run. Numbers therefore differ slightly from prior reports; they are exact here.
- **Harnesses (reproducible):**
  - `benchmarks/oss_bench.py --repo <path>` — token economics + the discover↔validate signal.
  - `benchmarks/oss_features.py --repo <path>` — the full-command smoke matrix + the
    `discover → calibrate → validate` convergence test.
- **Method:** each repo is shallow-cloned at the commit below, then `bounds init --root` +
  `bounds discover --apply` bootstraps `.bounds/`, exactly as a real user (or `bounds guide`) would.
  All token counts are deterministic; the cloned SHA is recorded so every row is reproducible.

> **Tokenizers are not interchangeable.** cl100k_base is OpenAI's encoding; Claude/Gemini tokenize
> differently. The *reduction ratios* are stable across tokenizers (same order of magnitude); the
> absolute token counts are cl100k-specific.

## Headline (honest)

Across **13 supported-language repos** (Python, TypeScript, JavaScript) and **3 unsupported ones**
(Go, Rust, Java) used as fail-soft probes:

1. **It runs everywhere without crashing.** 456 command invocations across all 16 repos — **zero
   crashes, zero leaked tracebacks.** The fail-soft contract holds on real third-party code.
2. **Extraction is correct.** Every symbol spot-check across the corpus confirmed a *real,
   genuinely-exported* symbol (verified against source with grep). **No fabricated exports.**
3. **Retrieval economics are real but the headline baseline is generous.** Whole-repo orientation
   (`bounds list`) is 98.7–100% smaller than reading *all* source — but almost nobody reads an
   entire repo, so that ratio overstates real savings. The meaningful number is targeted retrieval:
   a `describe <subsystem>` is a **median of ~150–970 tokens**, occasionally **tens of thousands**
   for a fat-API subsystem (zod's `core` = 35,493 tokens). It scales with *exposed API*, not files.
4. **The auto-discover → validate/calibrate drift layer does not generalize.** **0 of 13** supported
   repos produced a clean `validate` after a fresh `discover`, and **0 of 13** reached a clean state
   even after the documented `calibrate --apply` remediation. The cause is a real bug (below), not
   just noise: `discover` emits overlapping/nested subsystem paths that `validate`'s flat ownership
   model cannot represent, producing **false** structural-drift errors that contradict `describe`'s
   own `[verified]` output on identical, unchanged source.

**Bottom line for marketing:** lead with what is true and verified — *correct, language-agnostic
extraction; cheap, targeted, tree-sitter-verified retrieval that scales with public API*. Treat
auto-`discover` as a **draft that needs human curation**, not a one-command path to a clean drift
gate. Do not imply a fresh `discover` validates clean — on this corpus it never did.

**What works mechanically:** every command ran, emitted the right shape (JSON by default; `--human`
re-renders the same data), and exited with a sensible code. The **blocking gates behaved correctly**
— `preflight`, `validate --enforce on`, and `calibrate --check` exited `1` whenever error-tier
issues existed, and `0` otherwise (express/lodash, whose only issues are warning-tier orphan
exports, pass the gate). `validate --quick` correctly narrows to changed files.

**What does not work:** the **remediation path does not converge.** `calibrate --apply` *reduces*
issues (documenso 7,235→4,264, zod 3,025→1,871, flask 314→173) but **never reaches zero on any
repo**, and on pure-JS repos (express 53→53, lodash 15→15) it changes nothing. So a user who
follows the documented flow — `discover` → (issues) → `calibrate` → (still issues) — has no
one-command route to a clean gate. The residue is two things: **(a)** expected orphan-export noise
on libraries (see §4), and **(b)** the nested-path false-drift bug (§4, BUG-1) that `calibrate`
cannot fix because it stems from file *ownership*, not from a declared-vs-actual export mismatch.

## 4. Issues surfaced by this benchmark

These were found by running the documented workflow on real repos and adversarially spot-checking
the output. Severity is from an *end-user-trust* standpoint.

### BUG-1 (HIGH) — `discover` and `validate` disagree on identical, unchanged source

Affected: click, flask, requests, fastapi, httpie, axios, date-fns, zod, chalk, nest, documenso
(9–11 of 13, depending on layout).

On a fresh `discover --apply`, `validate` reports `E_STRUCTURAL_DRIFT` errors of the form
*"subsystem 'X' declares 'Sym' in exposes but no source file exports it"* — for symbols that
`describe X` **simultaneously lists as `[verified]` exported** and that grep confirms are genuinely
exported. The tool contradicts itself on an unmodified checkout.

**Root cause (pinned in source):** `discover` can emit **nested/overlapping** subsystem paths (a
parent dir and one of its subdirectories both become subsystems — e.g. flask `src/flask` nesting
`src/flask/json`; click `tests` nesting `tests/typing`; documenso package roots nesting `lib`
subdirs). `validate` uses a **flat, single-owner** model: `engine.py:84` assigns each file to the
**sort-earlier** subsystem (`if rel in file_owner: continue  # first declared owner wins`), so the
parent claims the child's files. `checks.py:75–86` (`actual_exports`) then counts exports only from
**owned** files, so the starved child owns **zero** files → every symbol it declares "drifts," and
the *same* symbols re-appear as `info` undeclared-exports on the parent. Reproduced minimally on
chalk (`supports-color` declares 11 symbols `validate` then can't find) and click (`typing`
subsystem, 10 symbols).

**Fix direction:** the engine documents a *flat topology* assumption that `discover` violates. Fix
either (a) make `discover` emit a true partition (a parent path excludes files owned by a more
specific child), or (b) make ownership **most-specific-path-wins** (deepest declared path owns the
file — the same longest-prefix principle used for tsconfig alias resolution). Needs its own change
with regression coverage; not fixed in this pass.

### BUG-2 (MEDIUM) — `discover` emits overlapping (non-partitioning) subsystems with no warning

The structural cause of BUG-1, but independently a quality problem: `discover` can produce a set
where one subsystem's path is a strict subdirectory of another's (or a `root=.` catch-all owning the
whole repo, as on lodash and zod), so files double-count across manifests. `discover --apply` emits
`notes: []` and no ambiguous-ownership warning. At minimum it should warn; ideally it should not
produce overlaps.

### BUG-3 (MEDIUM) — `discover` writes `consumes` edges to subsystems it never creates

Affected: click, flask, requests, fastapi, express, nest. `discover` detects a dependency target and
writes `consumes: <name>`, but never materializes `<name>` in `root.yaml`, so `validate` then raises
a self-inflicted `E_UNRESOLVED_REFERENCE` ("consumes unknown subsystem 'complex'") on a fresh run.
Examples: click `commands → complex`; requests `tests → testserver`; express writes 19 consume-edges
to example dirs but only materializes ~3.

### BUG-4 (MEDIUM, **fixed in this pass**) — `init`/`discover` hardcoded `languages: [python]`

`cli.py` `_ROOT_TEMPLATE` wrote `languages: [python]` and `discover` never overwrote it, so
`documenso` (pure TS/Prisma/SQL) and every unsupported-language repo declared `languages: [python]`.
**Fixed:** `discover` now derives `languages` from the extracted source and writes it authoritatively
(`discover.py`); verified on chalk → `[typescript]`, requests → `[python]`. Regression test added.

### BUG-5 (LOW) — `bounds where <file>` returns 0 results for a manifest-owned file

Affected: click, zod. A symptom of BUG-1's ownership starvation: `where` for a file owned by a
starved nested subsystem returns "no matches" even though the file exists and is in a manifest's
`paths`. (Note: `where` takes a *symbol* by default; the file-path case is a separate UX wrinkle.)

### BUG-6 (LOW) — symbol kind/file mis-labeling on overloaded names and some TS declaration forms

Affected: fastapi, nest, chalk, documenso. Not *false* exports (the symbols exist and are exported)
but imprecise labels: fastapi `Body` labeled `kind=function` points at the class def, not the
exported function; nest `HttpStatus` (an `export enum`) labeled `kind=const`; chalk
`export class Chalk` labeled `const`. Could misdirect an agent navigating to a definition.

### BUG-7 (LOW) — `overview` reports `health.ok=true` while `validate` reports many issues

Affected: date-fns (ok=true with 1,108 validate issues incl. 948 errors), lodash. `overview` health
only counts schema errors + cycles, so it reads "healthy" while `validate` disagrees. Inconsistent —
most repos correctly set `overview_health_ok=false`.

### BUG-8 (LOW) — `describe` JSON omits the file list its `--human`/`--full` view shows

Affected: lodash, date-fns. `describe` JSON has `file_count` (int) but `files: []`, while `--human`
and `--full` show the actual list. This violates the project's own **JSON-first invariant** (`--human`
must not expose information the JSON omits). Either populate `files` in JSON or stop showing it in
`--human`.

### BUG-9 (LOW) — `validate` exits `0` on a fatal `E_MANIFEST_NOT_FOUND`

Affected: chalk (after a no-op dry-run `discover`). `validate` printed a fatal error object but
exited `0`, which can mislead a script/CI into treating a missing-manifest fatal as success.

### Expected-but-noisy (not bugs, but a UX/marketing liability)

`E_ORPHAN_EXPORT` dominates almost every report (183/206 on click, 2,112/2,611 on fastapi, 1,751 on
zod) because a **library's** public API is consumed by external users, not by an in-repo subsystem —
so every export reads as "consumed by nothing." Technically correct, but it floods the report on the
single most common way someone tries Bounds (point it at a library). Consider a role-aware
suppression (a `library`/`public-api` role whose exports are not expected to be internally consumed)
or demoting these to `info`. Until then, do not market `validate` as "clean drift control out of the
box" — on a freshly-discovered library it is a wall of warnings.

## 5. What this means for the marketing claims

- **Keep:** "tree-sitter-verified public surface, extracted deterministically" — measured correct,
  zero fabricated exports, across Python/TS/JS.
- **Keep, but show the spread:** "a `describe` is cheap" → *"median a few hundred tokens; scales with
  exposed API, so a large public-API subsystem can be 15k–35k."* Don't state a flat "a few hundred
  tokens" without the tail.
- **Reframe:** the 99%+ "map reduction" → it compares against reading **all** source. Present it as
  "orientation is near-free" and lead with the **targeted-retrieval** comparison instead.
- **Qualify:** API reduction is **54–100%** depending on subsystem size — cite the range, never a
  single flat percentage.
- **Add an honest caveat:** `discover` produces a **draft** to curate; a fresh `discover` does not
  validate clean (0/13 here) and `calibrate` does not make it clean (0/13). Frame the drift gate as
  something you reach *after* curating contracts, not a one-command guarantee.
- **Cite the corpus:** "measured on 13 OSS repos across Python/TS/JS at the commits in
  `benchmarks/results/oss-cross-language.md`," not "measured on 2 repos."

## Fixes landed in this branch (`agent-plugins-aliases-benchmark`)

Several issues this benchmark surfaced were fixed in the same pass; the rest are tracked in
[docs/known-issues.md](../../docs/known-issues.md). The headline: a **fresh `discover → validate` on
a real library is now clean of false positives.** Validate issue counts on an unmodified checkout,
before → after:

| Repo | before | after | what's left |
|------|------:|------:|-------------|
| click | 206 | **3** | 2 real boundary violations (tests import internals) + 1 coverage note; `ok: true` |
| flask | 314 | **19** | residual TS-free drift + boundary edges |
| requests | 146 | **6** | |
| express | 53 | **1** | a coverage note; 0 errors |
| axios | 191 | **59** | boundary edges + TS type-export drift |
| zod | 3,025 | **166** | TS `export type` drift on the 831-export `core` (BOUNDS-008) |

- **BOUNDS-001** (most-specific-path ownership) — false structural drift from nested subsystem paths: click 20→0, flask ~133→11.
- **BOUNDS-002** — `discover` no longer writes consume-edges to unmaterialized subsystems (click unresolved 1→0).
- **BOUNDS-003** — `discover` writes detected `languages`, not a hardcoded `[python]`.
- **BOUNDS-004** — tsconfig path aliases honor TypeScript's longest-prefix rule.
- **BOUNDS-005** — mapping coverage is now measured + surfaced loudly (see below).
- **BOUNDS-012** — orphan-export no longer floods libraries (click 183→0): orphan detection needs interface-level contracts, which `discover`'s coarse edges don't provide.

The dominant residual is **BOUNDS-008** (TypeScript `export type`/re-export under-detection) — the next correctness lever for clean fresh-discover on TS-heavy repos.

### New: honest mapping coverage (BOUNDS-005)

`validate` and `discover` now report how much **source** Bounds actually mapped, with a by-language
breakdown of what it could not, and a loud `E_COVERAGE_GAP` warning + next step when it's < 100% —
so a polyglot repo can't look fully mapped while an unsupported language sits dark. Example on a
3-Python + 5-Go repo: *"mapped 37.5% of source (3/8 files); unmapped: 5 in unsupported languages
(go×5)"* with a concrete fix. See [docs/coverage.md](../../docs/coverage.md).

## Roadmap implications — should Go/Java/Rust come next?

**Recommendation: polish the supported languages first; add new ones after.** The evidence:

- The *core* (extraction + retrieval economics) already generalizes — it was correct and crash-free
  across Python/TS/JS. The *contract layer* (discover/validate) is what had the bugs, and those bugs
  (BOUNDS-001/008/012) are **language-interacting** (TS type exports, nested packages). Adding Go/
  Java/Rust now would multiply that surface across more ecosystems before it's solid on three.
- Fail-soft on unsupported languages already works (no crash, 0 subsystems), and **BOUNDS-005 makes
  the gap honest and loud** — so there is no correctness emergency forcing new adapters; a polyglot
  repo is now truthful about what it didn't map and tells the user how to fill it.
- Each new language is a real adapter (tree-sitter grammar, export semantics, ORM/table detection) —
  best added once the Python/TS/JS contract layer is clean enough to market without caveats.

So: **finish BOUNDS-008 (TS type exports) and tighten boundary inference, then add Go/Java/Rust** as
genuinely additive adapters. The fail-soft + coverage-gap path is the honest bridge until then.
